# 显存互斥与上下文预算（8GB 卡的两条铁律）

## 铁律一：同一时刻只能跑一个后端

8GB 显存装不下两个「大模型后端」。本机实测的三个后端：

| 后端 | 端口 | 用途 | 显存占用 |
|---|---|---|---|
| llama-swap（llama.cpp） | 8080 | 多模型路由，≤80K 上下文，预填充最快 | 5.5-6.0GB |
| 长上下文引擎（NInfer 系） | 8091 | 单模型 256K 上下文 + 视觉 | 7.6-7.8GB |
| KV 外置引擎（KVMem 系） | 18202 | 超长上下文，KV 历史常驻内存 | 7.4GB |

启动第二个 = 第一个的部分层被挤到 CPU，**症状不是报错，是掉速**：

```
模型照常回答，速度从 30 tok/s 掉到 5-10 tok/s
```

排查第一步永远是看显存：

```bash
nvidia-smi --query-gpu=memory.used,memory.free --format=csv,noheader
```

如果剩余 < 500MB 而按模型体积算本该有余量，就是有别的进程在抢。

**特例：ComfyUI 常驻会额外吃掉约 1.9GB**。出图时它不走，等于把 5.5-6GB 的大模型挤出显存。所以「出图 + 大模型对话」不要同时开。

## 铁律二：上下文不是越大越好，128K 是崩塌点

同一台机器、同一个 27B 模型，只改上下文长度，测预填充速度：

| 上下文 | 预填充速度 | 现象 |
|---|---|---|
| 80K | 2,370 tok/s | 流畅 |
| 96K | 明显下降 | 开始劣化 |
| **128K** | **63 tok/s** | **崩塌**（掉约 40 倍） |
| 192K | 13.6 tok/s | 不可用 |

原因：KV 缓存放不进显存时，预填充阶段要在显存与内存之间反复搬运，PCIe 成为瓶颈。8GB 卡的「安全上限」是 **80K**。

### 算一下 KV 缓存的账

| KV 精度 | 每 token | 80K 上下文总占用 |
|---|---|---|
| f16 | 64 KiB | 约 5.2GB |
| q8_0 | 约 34 KiB | 约 2.7GB |
| **q4_0** | **18 KiB** | **约 1.4GB** |

所以 8GB 卡跑 5.5-6GB 的模型，**必须**：

```
--cache-type-k q4_0 --cache-type-v q4_0
```

否则大上下文必然溢出（表现为预填充崩塌，不是 OOM 报错）。

## 模型体积与能否共存

| 模型档 | 权重 | 上下文 | 能否共存 |
|---|---|---|---|
| 27B 级 | 5.5-6.0GB | 80K | ❌ 必须独占 |
| 9B 级 | 4.9-5.0GB | 32-64K | ❌ 独占（勉强） |
| 4B 级 | 2.5-2.8GB | 16-32K | ⚠ 与更小的模型共存风险高 |
| 1.8B 翻译 + 0.6B 向量 | 1.78 + 0.60GB | 8K | ✅ 唯一稳定共存组合（2.4GB） |

**结论**：任何 ≥4.8GB 的模型，都按「独占」规划。

## 视觉塔：用 CPU 换显存

多模态模型的视觉编码器需要额外显存：

| 方案 | 显存 | 结果 |
|---|---|---|
| GPU 视觉 | +1.4GB 运行时预留 | 8GB 卡启动失败：`requested Engine runtime reservation requires X bytes, but only Y available` |
| **CPU 视觉** | **0** | 每张图编码多几秒，功能完整 |

8GB 卡的结论：**视觉一律走 CPU**。

## 一个反直觉的经验

上下文「能开」和「好用」是两件事。256K 窗口确实开得起来（实测灌入 23.2 万 token，预填充 418 tok/s，检索 3/3 命中），但那是把 KV 历史放到内存、按相关性捞回的有损方案——**长篇小说的人物细节会「记错」**。

分工建议：

| 场景 | 方案 |
|---|---|
| ≤80K 日常对话/写作 | llama.cpp 全显存（预填充快 7 倍） |
| >80K 长文/全文检索 | 长上下文引擎或 KV 外置（慢，但窗口大） |
| 需要视觉 | 视觉走 CPU 的那套 |
