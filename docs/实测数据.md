# 实测数据与测量方法

> 所有数字来自同一台机器：RTX 4070 Laptop 8GB / 24GB RAM / Windows 11。
> 单人、单次即可复现；不同型号的显存带宽与功耗墙会带来差异，请把数字当**量级**参考。

## 一、速度测量口径

**解码速度（tok/s）**：固定 prompt，`max_tokens=512`，`temperature=0`（贪心）或 0.7（采样），
用客户端侧 wall-clock 计算：`(输出 token 数) / (从首 token 到末 token 的秒数)`。
不同口径（含/不含首 token 延迟）能差 30%，比较时必须同口径。

**预填充速度（tok/s）**：喂固定长度文本，测量「从请求发出到首 token 到达」的秒数，
`输入 token 数 / 该秒数`。这是长上下文场景最关键的数——它决定了你等多久才见到第一个字。

本仓库的测量脚本：`scripts/bench_stream.py`（任何 OpenAI 兼容端点通用）。

## 二、27B 三元量化模型（PTQ1，权重 5.94GB，256K 上下文）

| 场景 | 速度 | 备注 |
|---|---|---|
| 中文长文创作（采样） | **28 tok/s** | MTP 接受率约 15%——创作文本的固有特性 |
| 高度重复性文本 | **82 tok/s** | MTP 接受率 96%，投机解码在这种文本上最赚 |
| 贪心解码 | 38 tok/s | 确定性输出 |
| 预填充 1.37 万字 | **834 tok/s** | 长文灌入的典型场景 |
| 预填充 23.2 万 token | 418 tok/s | 极限压测，仍可用 |
| 三针检索（长文里找三个位置） | 3/3 命中 | 256K 窗口的有效性验证 |

> **解读者注**：MTP（多 token 预测）的收益高度依赖文本的可预测性。
> 同一模型，写小说 28 tok/s、生成格式化表格 82 tok/s——差 3 倍。
> 所以「某模型多少 tok/s」这个说法本身意义不大，必须绑定场景。

## 三、上下文长度 vs 预填充速度（同一模型，只改长度）

| 上下文 | 引擎 | 预填充 | 现象 |
|---|---|---|---|
| 80K | llama.cpp | **2,370 tok/s** | 全显存，最快 |
| 96K | llama.cpp | 明显下降 | 开始劣化 |
| 128K | llama.cpp | **63 tok/s** | 崩塌 |
| 192K | llama.cpp | 13.6 tok/s | 不可用 |
| 131K | KV 外置引擎 | 332 tok/s @2.5 万 token | 平坦扩展 |
| 131K | KV 外置引擎 | 304 tok/s @3.6 万 token | 不随长度衰减 |

**结论**：
- 日常（≤80K）用 llama.cpp，预填充快 **7 倍**
- 超长上下文用 KV 外置/分页方案，慢但窗口大，且速度随长度下降平缓
- 直接开 128K 是最差的选择：既不快，也不好用

## 四、多模态：视觉塔放 GPU vs CPU

| 方案 | 单图耗时 | 显存 | 可用性 |
|---|---|---|---|
| GPU（`--vision`） | — | +1.4GB 运行时预留 | ❌ 8GB 卡启动失败 |
| CPU（`--vision-cpu`） | 约 10-15 秒/图 | 0 | ✅ 完整可用 |

实测一张 1.5MB 的 990×1080 插画：端到端 20 秒返回（含视觉编码 + 推理），图像编码约 277 个 token。

## 六、复现步骤

```bash
# 1. 起服务（见 README）
# 2. 测解码速度
python scripts/bench_stream.py --base http://127.0.0.1:8091/v1 --model your-model --tokens 512

# 3. 测预填充（喂长文本）
python scripts/bench_stream.py --base http://127.0.0.1:8091/v1 --model your-model --prompt-file long.txt --prefill-only
```

得到的数字与上表偏差在 ±30% 内属正常（取决于散热状态、内存频率、后台进程）。
